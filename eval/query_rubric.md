# 查询 Agent：评分标准（M19）

**冻结时间：2026-11-16，在留出题上第一次运行之前提交。** 之后发现的问题另行记录，不改这一版，也不改题目和参考 SQL。

## 要检验什么

原来的 Agent 只能调用写好的几个工具，工具没覆盖的问题答不了，换一份数据要改代码。M19 加了一个查询 Agent：它把分析请求写成只读 SQL，程序执行后交出一张结果表（[analyst.py](../src/da_agent/analyst.py)）。

让模型写 SQL，最怕的是它交出一个看起来没问题、其实算错了的数。所以这次量四件事：

1. 它算出来的数对不对（和人写的参考 SQL 逐个数对比）。
2. 数据里没有答案时，它会不会老实说答不了。
3. 把口径做成现成的列和表达式（口径配置），比只用文字写口径，结果差多少。
4. 换一份没有任何配置的数据（CSV），不改代码，它还行不行。

安全（只读、不能读写文件）不靠评测，靠测试保证（[test_sqlrun.py](../tests/test_sqlrun.py)）；评测里只统计被检查挡下的语句有多少条。

## 题目（[query_cases.yaml](query_cases.yaml)）

- **开发题**（10 道）：写提示词时用。跑了一次，20/20 算对，提示词没有改过。**成绩不算数。**
- **留出题**（36 道），写完之后没有用模型跑过：
  - 固定工具也能答的 12 道（周指标、环比同比、按国家 / 新老客 / 商品拆）。参考 SQL 的结果另有测试和固定工具核对一致。
  - 固定工具答不了的 10 道（按星期几、按小时、按月和季度、复购、高频客户、按净销售额排商品等）。
  - 没有口径配置的 CSV 11 道（Online Shoppers 8 道、Bank Marketing 3 道）。
  - 应该拒答的 3 道（要利润但没有成本、日期超出数据范围、要订单金额但数据里没有）。

电商的 24 道题在两份配置上各跑一遍：`retail`（口径做成了列和表达式）和 `retail_raw`（同一份数据，口径只写成文字）。每道题每份数据跑 2 次，共 120 次运行。模型：MiniMax-M3.1-Flash-Preview。

参考 SQL 是人写的，电商题在清洗后的基础表上执行，不经过口径配置里的表，和查询 Agent 走的是两条路。

## 怎么打分（程序判定，[query_eval.py](../src/da_agent/query_eval.py)）

每次运行是四种结局之一：

| 结局 | 含义 |
|---|---|
| 算对 | 结果表里找得到参考结果的每一个数；应该拒答的题没有提交结果 |
| 交了但不对 | 交了结果，但有数对不上；或者应该拒答的题交了结果。**最要紧的一种** |
| 该答没答 | 应该回答的题，它说答不了 |
| 没跑完 | 次数用完、模型一直报错等，没有结果 |

细则：

- 有 keys 的题（按国家、按商品等），数要出现在对应的那一行；没有 keys 的题，数出现在结果表任何位置都算。
- 数值允许按结果自己的小数位四舍五入，此外相对误差不超过 0.5%；比率写成小数或百分数都算。
- 结果的行数不能超过参考结果的行数 + 5（防止把整张表倒出来碰运气）。
- 模型接口报错（限流、超时）的运行等一会儿重跑，最多 4 次；这不是查询 Agent 的表现。重跑次数照实记录。

## 结论的标准（运行前定下）

| 结论 | 要求 |
|---|---|
| 把查询 Agent 作为工具接进原来的 Agent（M19b） | `retail` 配置上 48 次运行：算对 ≥ 90%（≥ 44 次），并且“交了但不对”不超过 2 次 |
| “换一份数据不用改代码”这句话可以说 | CSV 的 24 次运行：算对 ≥ 80%（≥ 20 次），并且“交了但不对”不超过 2 次 |
| “口径配置有用”这句话可以说 | `retail` 的算对比例比 `retail_raw` 高 10 个百分点以上。达不到就写“没有测出差别” |

没达到第一条：查询 Agent 只保留为单独的命令（`da-agent query`），不接进原来的 Agent。

## 打分本身可能出错

程序打分会有误判（参考 SQL 写错、请求有两种合理的读法、评分太死）。处理办法：

- 标题数字用程序的打分，原样报告。
- 每一条“交了但不对”和“该答没答”，逐条回到参考 SQL 和结果表判断：是真的算错，还是题目或评分的问题。判断和依据写进结果目录的 `adjudication.json`，并在结论里另列一行“复核后”的数字。
- 判断的是 Claude（代项目作者，作者本人未逐条核对）。

## 已知的局限（运行前写下）

- 题目、参考 SQL 和查询 Agent 是同一个 AI 写的，可能有共同的误解。固定工具也能答的 12 道另有独立的核对，其余没有。
- 请求写得很明确（指定了周、指标、排序方式）。真实用户问得更含糊；把含糊的问题变成明确的请求是原来那个 Agent 的事，这一轮不测。
- 只有一张表，没有测多表关联。
- 只测了一个模型，每道题只跑 2 次。
- 留出题和开发题的题型相近（都是聚合、排序、对比）。
- “算对”只说明数对；它写的口径说明、注意事项写得好不好，这一轮不评。
