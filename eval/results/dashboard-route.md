# 看板 Agent 接进主 Agent：评测结果和结论（M22）

> 评分标准 [dashboard_route_rubric.md](../dashboard_route_rubric.md) 和题目在留出题运行前提交（f7781e0，2026-11-22 17:16:52；运行开始于 17:17）。打分由程序完成；未通过的运行和每个看板由 Claude 代项目作者复核（作者本人未逐条核对）。模型：MiniMax-M3.1-Flash（主 Agent、查询 Agent、看板 Agent 相同）。

## 结论

**三条事先定的标准都达到了，所以 `da-agent ask` 默认开启搭看板。复核发现一个多 Agent 之间的真实缺陷：查询 Agent 和看板 Agent 用的数据层不一致，新老客这类看板搭不出来。**

| 运行前定的标准 | 结果 | 达到了吗 |
|---|---|---|
| 分得清：该搭的搭了、不该搭的没搭 ≥ 15/16 | 16/16（把“试了但没搭出来”也算没分清：15/16） | 达到 |
| 接得上：要看板的 8 次里看板搭出来 ≥ 7 | 7/8 | 达到 |
| 程序判定通过 ≥ 13/16 | 13/16 | 达到（压线） |

复核后：要看板的 8 次里，搭出来**并且对题**的 6 次；新老客那道题两次都没做到。只是提问的 8 次全部没有误搭看板。

## 做了什么

看板 Agent 早就有（M13 的自主搭看板：模型写方案，程序校验口径、算数、画图）。M22 把它做成主 Agent 的工具 `build_dashboard`，系统里现在有四个角色：

| 角色 | 负责 | 交出来的东西由程序怎么把关 |
|---|---|---|
| 主 Agent | 理解问题、决定用哪个工具、写报告 | 答案里每个数字核查出处，找不到退回修正 |
| 查询 Agent | 写只读 SQL 取数 | 只读数据库、只收一条 SELECT；交出去的是程序执行的结果表 |
| 看板 Agent | 设计看板 | 方案校验口径；结论里的数必须在图的数据里；“最高 / 最低”说法和数据核对 |
| 复核 Agent | 挑错（单独命令） | 引用必须是答案原文，依据必须是真实的工具调用 |

接入的细节：

- 交回给主 Agent 的是程序生成的东西：页面位置、每张图的标题和结论、程序自动发现的数据问题。看板 Agent 自己写的说明放在 `unverified_notes` 里，不当出处。
- 没搭出来时工具报错，主 Agent 可以把目标缩小再试；**一次回答最多搭 2 次**，由程序强制（搭一次要几分钟、几十万 token）。
- 开发题里发现看板方案没办法限定时间段（“给财务看 2010 年”连续两次把工具次数用完），给方案加了 `period`；之后同一道题一次搭成。
- 界面里打开“允许搭看板”，搭好的看板直接嵌在结果里。

## 发现的问题

**一、两个 Agent 的数据层不一致（最重要）。** 查询 Agent 用的是口径配置里的表（有“新客 / 老客”这一列）；看板 Agent 用的是 M13 的交易表，没有这一列。新老客看板因此搭不出来：一次看板 Agent 两次都把工具次数用完；另一次搭出了看板，但里面只有活跃客户数、人均订单数，没有新老客。主 Agent 甚至在请求里写了“用 order_lines 的 customer_type 字段”——那是查询 Agent 的表，看板 Agent 看不到。修法是让看板 Agent 也用同一份口径配置，下一步做。

**二、主 Agent 写的目标太长。** 要看板的 8 次里有 5 次，第一次写的目标超过 300 字被退回，白跑一轮（不占“最多 2 次”的名额）。

**三、成本很高。** 要看板的运行：用时中位数 619 秒（228–1,284 秒），token 中位数 61 万（41 万–120 万）。只是提问的运行：用时中位数 71 秒、token 中位数 12 万，和以前差不多。

**四、数字出处的老问题还在。** 3 次未通过里有 2 次是回答里写了心算或没算过的数（一次还声称是 calculate 算的）。

## 局限

- 题目只有 8 道，每道 2 次；题目和提示词是同一个 AI 写的。程序判定的通过数刚好压线（13/16）。
- 边界题（“给我看一下排名”不该搭看板）的判定是事先定的，换一个人可能判成该搭。
- 看板好不好看、图选得对不对，这次只看了“是否对题”；看板本身的质量靠 M13 的程序校验和以前的评测。
- 只用了电商数据。

uv run da-agent ask "上周 GMV 为什么变化？" --no-dashboard
