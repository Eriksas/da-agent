# 把查询 Agent 接进原来的 Agent：评测结果和结论（M19b）

> 评分标准 [query_e2e_rubric.md](../query_e2e_rubric.md) 和题目在留出题运行前提交（c4b0d0e，2026-11-17 00:35:08；运行开始于 00:37）。打分由程序完成；未通过的运行由 Claude 代项目作者逐条复核（作者本人未逐条核对）。模型：MiniMax-M3.1-Flash（主 Agent 和查询 Agent 相同）。

## 结论

**两条事先定的标准都达到了：固定工具答不了的问题，接入取数后从 4/20 到 15/20；原来的题没有变差。所以 `da-agent ask` 默认开启取数。代价是原来那类问题的成本约为 2.7 倍。**

| 运行前定的标准 | 结果 | 达到了吗 |
|---|---|---|
| 新题：`agent_query` 通过 ≥ 14/20，并且比 `agent_skill` 多 ≥ 6 次 | 15/20 对 4/20，多 11 次 | 达到 |
| 回归题：`agent_query` 不少于 `agent_skill` 减 3 | 29/30 对 28/30 | 达到 |

复核后：新题上 `agent_query` 18/20（3 次未通过是评分的问题，2 次是答案引用了没有出处的数），见下文。

## 做了什么

原来的 Agent 只能调用写好的固定工具：某一周和上周 / 去年同周比的指标、拆解、下钻。按星期几、按小时、按季度、复购、某一群客户这些问题它答不了。M19 做了一个查询 Agent（写只读 SQL，程序执行，[评测](query-agent.md)）；M19b 把它做成原来那个 Agent 的一个工具 `query_data`：

- 主 Agent 负责理解问题、写一个明确的取数请求（时间范围、指标、分组、筛选、排序），再解读结果、写回答。
- 查询 Agent 负责写 SQL；程序在只读数据库上执行，交回一张表。
- 交回去的表里的数可以当出处；查询 Agent 自己写的口径说明和提醒放在 `unverified_notes` 里，**数字核查不把它当出处**。原因：M19 里发现它会在说明里编原因（把 11 月 27 日说成“圣诞前夕”）。
- 嵌套运行的完整记录附在主运行的 `sub_runs` 里，每一次取数都能追溯到它写的 SQL。
- 不开启时，工具列表和提示词与以前一字不差（有测试）。

## 未通过的 5 次（加上取数的一组），逐条复核

| 题目 | 程序判的原因 | 复核 |
|---|---|---|
| 毛利率 第 2 次 | 违规说法 | **评分的问题**：规则命中的是“无成本 ≠ 毛利率为 0 或很高，只是无法计算”，这句话正是在拒绝估算 |
| 周日客单价 第 1、2 次 | 1 个数字没有出处 | **评分的问题，核查程序的缺陷**：答案原样照抄了工具结果里的 0.13109840352143715；17 位小数时容差减去浮点余量成了负数，永远对不上。已修（`checks.within`），这次的程序打分仍按修之前的代码 |
| 10 月海外 第 1 次 | 3 个数字没有出处 | **真的违规**：引用了查询 Agent 说明里的 9,466.56 和 22.7%，以及一个没有出处的订单数 216。拦住这种引用正是 `unverified_notes` 的用意 |
| 前 10 客户 第 1 次 | 4 个数字没有出处 | **真的违规**：答案自己说“2011 年只有 343 天数据”并据此算日均，343 没有出处 |

两次真的违规里，题目要的数都是对的，错在答案多写了没有出处的数。判断和依据在 [adjudication.json](e2e-2026-11-17-new/adjudication.json)。

## 成本：原来的题上贵了约 2.7 倍

原来的 15 道题，加上取数后 30 次运行里有 22 次用了取数，平均约 2 次。它不是放着固定工具不用，而是用完固定工具后**再取数深挖**：银行假日那周逐日拉 GMV 确认少了一个交易日，小样本那道题把澳洲的订单逐张拉出来。通过数没有变（28 → 29），也就是说这些深挖在评分上看不出好处；答案是不是因此更有说服力，这次的评分量不出来。

新题上反过来：只有固定工具的一组反复调用工具、找不到答案，平均 191 秒；加上取数后 116 秒。

按事先的约定，成本不设门槛、照实记录。降低成本的办法（例如限制每次回答最多取数几次、或者在提示词里要求“固定工具已经回答了就不再取数”）要改提示词，改了要重新评测，这一轮没有做。

## 中途中断的处理

新题评测在 2026-11-17 01:29 跑完前 5 道题（每道 4 次）后进程被外部中断（没有报错，同时运行的另外两组正常结束）。剩下 5 道题在 19:02 起用同样的代码和评分规则补跑，然后合并、用同一套规则重新汇总。没有任何一次运行被重跑；中断前已经跑完的结果原样保留。meta.json 里写明了经过。

## 局限

- 新题只有 10 道，每道 2 次；题目、参考 SQL、取数说明是同一个 AI 写的。
- 新题的正确数值只有一种口径（例如“占全年 GMV”按全部 GMV 算）。
- 回归题是以前反复用过的题；在它们上面没有变差，不代表在别的问题上也不变差。
- 只测了一个模型。主 Agent 和查询 Agent 用的是同一个模型。
- 换了默认模型（Preview → 正式版），所以这次两组都重跑了；和以前在 Preview 上的成绩不直接比较。

## 重现

```bash
uv run da-agent ask "2011 年 11 月，一周里哪天卖得最好？"          # 默认开启取数
uv run da-agent ask "上周 GMV 为什么变化？" --no-query             # 只用固定工具
uv run da-agent eval --case-file eval/query_e2e.yaml --conditions agent_skill,agent_query --repeats 2 --name <新名字>
```
