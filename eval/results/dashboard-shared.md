## 做了什么

M22 复核发现两个 Agent 的数据层不一致：查询 Agent 用口径配置里的 `order_lines`（新客 / 老客、周、月、带口径的金额列都算好了），看板 Agent 用 M13 的交易表（没有这些列）。看板 Agent 不能写 SQL，只能对已有的列做聚合，所以新老客这种需要先算“每个客户第一次购买在哪一周”的看板，它搭不出来。

M23 让两个 Agent 读同一份配置 [semantic/retail.yaml](../../semantic/retail.yaml)：

- **同一张表**：看板的新数据源 `semantic:retail` 以只读方式打开查询 Agent 用的同一个数据库文件（同样关闭外部访问）。
- **同一套指标口径**：配置里 9 个指标各加了一份“看板写法”（例如客单价 = ratio(GMV, 订单数)）。测试核对每个指标的看板写法和查询 Agent 的 SQL 写法算出来一样：测试数据上整体、逐周、逐国家、逐月、逐客户类型，真实数据上逐周、逐国家（9 个指标 × 100 多周）。查询 Agent 的 SQL 写法以前已经逐周和固定工具核对过。
- **程序把关**：看板里和配置同名的指标（id 或显示名相同，“GMV（英国）”也算同名），定义必须和配置一致，预览和提交都检查；可以多加筛选条件，配置里的条件一条都不能少。
- **规则也写在配置里**：amount 要按销售 / 取消区分、金额单位是英镑、GMV 可能被之后的取消抵消（按 GMV 给商品排名时，大部分被取消的商品会被标出来）。
- **查询 Agent 看到的完全不变**：看板写法不进它的数据说明。
- 旧的 `retail` 数据源保留，以前的看板还能重新生成。

## 发现的问题

**一、文字的周、月列会误导看板 Agent。** 口径配置的表里 week（“2011-W48”）、month（“2011-11”）是现成的文字列，看板 Agent 有时把它们当时间列、加上“按周 / 按月”，被退回 8 次（12 次里的 3 次）。会员那次没搭出来，有 3 次退回是这个原因；更多的是参数格式不对（把图包了一层、漏写字段）。可以在配置里标明这两列是文字标签、按时间画图用 order_time，留到之后做。

**二、新客口径按月、按年汇总时要小心。** 配置的新客是“第一次购买落在当周”。会员看板的指标卡“2011 年老客回购客户数（全年去重）”包含当年新来、之后又买的客户，所以新客数 + 老客数 > 购买客户数。这是配置本来的口径，不算错，但读者可能把两个数相加。另外主 Agent 写给看板 Agent 的目标里把新客说成“当月首次购买”，和配置不一致；看板 Agent 用的是配置的口径。

**三、新加的同名检查这次没有拦下任何东西。** 退回 0 次：看板 Agent 都照抄了 profile_table 给出的配置指标。它也没有误伤，但这次没法说明它防住了什么。

**四、只是提问的运行慢了一些。** 用时中位数 118 秒、token 16 万（M22 同样 4 道题：71 秒、12 万），取数次数相同（都是 15 次）。这部分的改动只有提示词里两行，原因没有单独查。

## 局限

- 题目只有 10 道，每道 2 次；题目、提示词和口径配置是同一个 AI 写的。
- `dashboard_columns` 只说明方案用到了这一列；用得对不对靠逐个复核。
- 成本下降的两个来源（目标上限放宽、表里有现成的列）没有拆开测。
- 只用了电商数据；财报、用户给的 CSV / Excel 没有口径配置，仍走原来的路。
