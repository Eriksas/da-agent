# 看板 Agent 接进主 Agent：评分标准（M22）

**冻结时间：2026-11-22，在留出题上第一次运行之前提交。** 之后发现的问题另行记录，不改这一版，也不改题目。

## 要检验什么

看板 Agent 早就有了（M13 的自主搭看板，单独评测过：两份盲测数据 13 次全部独立完成）。M22 把它做成主 Agent 的一个工具 `build_dashboard`：用户在对话里说要看板，主 Agent 写出“给谁看、判断什么”，交给看板 Agent 去搭。

所以这次不再评“看板搭得好不好”，只评接上之后新出现的两个问题：

1. **分得清吗**：用户要看板时搭看板，只是在提问时直接回答、不要搭看板（搭一次看板要几分钟、几十万 token）。
2. **接得上吗**：要看板时，看板真的搭出来了，回答里告诉了用户页面在哪。

## 题目（[dashboard_route.yaml](dashboard_route.yaml)）

- 4 道要看板：明说“看板”“仪表盘”“dashboard”的各一道，一道只说“做个页面，我想随时打开看看”。
- 4 道只是提问：环比、按星期几、为什么变化，以及一道边界题“给我看一下 2011 年各国的 GMV 排名”——说了“给我看”，但只是一个排名，按事先的判定应该直接回答。
- 开发题 3 道（[dashboard_route_dev.yaml](dashboard_route_dev.yaml)）写提示词时用过，成绩不算数。第一次跑（[route-dev-1](results/route-dev-1/summary.md)）3/3 通过，但“给财务看 2010 年”那道连续两次把看板 Agent 的工具次数用完：看板方案没办法限定时间段。为此给方案加了 period，并限制一次回答最多搭 2 次看板；同一道题再跑一次（[route-dev-2](results/route-dev-2/summary.md)），一次就搭成，用时 560 秒。

对比组只有一个：`agent_dashboard`（带流程 + 取数 + 搭看板，就是打算默认开启的配置）。每道题跑 2 次，共 16 次运行。模型 MiniMax-M3.1-Flash（主 Agent、查询 Agent、看板 Agent 相同）。

## 怎么算（程序判定）

- 要看板的题：必须**成功**调用 `build_dashboard`（调了但没搭出来不算），回答里要出现 `dashboard.html`（页面位置）。
- 只是提问的题：不能调用 `build_dashboard`（试着调用就算错）。
- 两类都要求：正常结束、答案里的数字全部有出处。只是提问的题不检查答案本身对不对，那部分以前的评测测过。

## 结论的标准（运行前定下）

| 结论 | 要求 |
|---|---|
| 分得清 | 16 次运行里，该搭的搭了、不该搭的没搭 ≥ 15 次 |
| 接得上 | 要看板的 8 次运行里，看板搭出来 ≥ 7 次 |
| 默认开启搭看板 | 上面两条都达到，并且 16 次里按程序判定通过 ≥ 13 次 |

都达到：`da-agent ask` 默认开启搭看板（`--no-dashboard` 关掉），界面里“允许搭看板”默认打开。没达到：保留为 `--with-dashboard` 选项，记录差在哪里。

另外照实记录（不设门槛）：每次运行的 token（含嵌套的 Agent）和用时；搭出来的看板逐个看一遍，标题和图是不是对着用户要的东西（Claude 代项目作者判断，作者本人未逐条核对）。

## 已知的局限（运行前写下）

- 题目只有 8 道，每道 2 次；题目和提示词是同一个 AI 写的。
- 边界题的判定（“给我看一下排名”不该搭看板）是事先定的，换一个人可能判成该搭。
- 看板 Agent 本身的质量这次不评；它搭出来的看板对不对，靠 M13 那套程序校验和以前的评测。
- 只用了电商数据。
